# Code-retrieval benchmark source notes

**Decision for JevGrep:** CORE-Bench Level 2/3 is the stronger source of repository-level tasks, provided that each search sees only its pre-change snapshot and the imported labels are audited. CoIR is useful as a separate snippet-ranking diagnostic; its published records do not directly support JevGrep's path-and-line evidence or cross-file coverage metrics. The fit judgments below are inferences from each benchmark's documented task and label format and [JevGrep's retrieval protocol](../specification.md#112-retrieval-benchmark).

## CORE-Bench (Zhang et al., 2026)

**Fit.** This is the code-retrieval CORE-Bench cited in the [roadmap](../../roadmap.md), not the homonymous scientific-reproducibility benchmark. Its Level 2 tests retrieval of code to edit for an issue; Level 3 tests retrieval of supporting code, tests, documentation, and configuration. These repository-state tasks are a closer match for JevGrep's evidence retrieval than Level 1's traditional snippet matching. The [original paper, v1](https://arxiv.org/html/2606.11864v1) reports Level 2 at 5,061 queries, 632 repositories, 9,377,120 corpus chunks, and 52,712 relevance judgments; Level 3 at 2,580 queries, 97 repositories, 2,609,581 chunks, and 106,479 judgments. Level 2/3 cover 11 languages. See the paper's Tables 1–2 and Sections 3.1–3.2.

**Availability and protocol.** The authors' [Hugging Face package](https://huggingface.co/datasets/zhangfw123/CORE-Bench) contains Level 2, Level 3, and rewritten-query variants; it deliberately omits Level 1. Per-repository directories contain `corpus.jsonl`, `queries.jsonl`, `qrels.jsonl`, and `qrels/test.tsv`. A rewrite reuses the original corpus and relevance labels. The [evaluation repository](https://github.com/zhangfw123/CORE-Bench-Eval) documents Git LFS download, a BM25 baseline, dense-model runners, and the modified MTEB protocol. The package is labelled **CC BY-NC-SA 4.0** on its dataset card; check that licence and the underlying repositories' licences before redistribution or commercial use. The Hugging Face viewer currently shows a schema-cast error for its mixed JSONL files, so use the documented file download rather than the viewer for ingestion. Sources: [dataset card](https://huggingface.co/datasets/zhangfw123/CORE-Bench), [evaluation README](https://github.com/zhangfw123/CORE-Bench-Eval#data-setup).

**What the labels mean.** Level 2 checks out the repository just before a pull request, chunks that snapshot, and marks chunks overlapping the eventual patch as relevant. The query is the issue or PR description after filtering for answer leaks and unusable requests. Thus its labels identify **actual edit sites**, not every file that might help diagnose the issue. Level 3 starts with those edit labels, then adds chunks seen in mini-swe-agent browse traces and accepted by an LLM-vote relevance filter. The authors compare agent resolution with Level 2 and Level 3 file allowlists as a functional check; they explicitly retain some useful traces even when the agent does not solve the issue. Thus Level 3 labels are useful but are partly agent- and judge-dependent, and neither level should be treated as an exhaustive set of all useful evidence. No curated no-answer split is described, so this dataset alone does not test JevGrep's negative-query accuracy. Sources: [paper v1, Sections 3.2.2–3.2.3 and Appendix E–F](https://arxiv.org/html/2606.11864v1), [dataset card, data layout](https://huggingface.co/datasets/zhangfw123/CORE-Bench).

**Leakage and held-out use.** The benchmark corpus is a **pre-PR snapshot**; the paper's evaluator merges and deduplicates chunks across repository snapshots for efficiency, then filters visible chunks by the query's repository and commit before scoring. A JevGrep adapter must reproduce that visibility boundary or future code and patches can leak into the search. The authors' separate fine-tuning data use repositories disjoint from the SWE-bench family, but the public benchmark package does not advertise a separate repository-disjoint train/dev/test partition for JevGrep; `qrels/test.tsv` is an evaluation-label file, not proof of an untouched holdout. Level 2 and 3 also share some instances and corpora. Reserve whole repositories and issue IDs for final evaluation, deduplicate across source suites and levels, and freeze the selected sample before tuning. Public, historical SWE-bench-derived requests can also have appeared in model training data; this is a limitation of a model-based JevGrep run, not a measured leak in the dataset. Sources: [paper v1, Sections 3.2, 3.4, 4.1 and Appendix B](https://arxiv.org/html/2606.11864v1), [dataset card](https://huggingface.co/datasets/zhangfw123/CORE-Bench).

**JevGrep measurement implication.** A bounded, repository-stratified Level 2 sample can test whether delivered excerpts cover patch-aligned edit ranges; Level 3 can separately test broader context recall. Map returned path and line spans to the supplied chunk/qrel spans, and report completion and output budget with coverage. The paper reports **NDCG@10 and Recall@100 on ranked chunks**; JevGrep's current retrieval pilot measures **delivered excerpts after selection and budget trimming**, so those scores are not directly comparable without an explicit ranked-chunk adapter. Avoid precision claims against these partial relevance labels. The paper itself notes weaker coverage of newly created or rapidly evolving repositories, uncommon project structures, and long-tail languages. Sources: [paper v1, Sections 4.1, Limitations, and Appendix D](https://arxiv.org/html/2606.11864v1), [JevGrep benchmark semantics](../../benchmarks/README.md#retrieval-pilot).

## CoIR (Li et al., ACL 2025)

**Fit.** CoIR gathers 10 datasets spanning text-to-code, code-to-text, code-to-code, and mixed text/code retrieval. Its text-to-code subsets are APPS (Python contest solutions), CoSQA (Python web-query/function pairs), and synthetic text-to-SQL. The JavaScript CodeSearchNet subset instead asks for a docstring *from code*; CodeSearchNet-CCR asks for a code suffix *from its prefix*. CodeFeedback includes JavaScript but pairs instructions with expected assistant replies. These are worthwhile model-level probes, yet they do not recreate a developer looking for behavior across a JS/TS repository. Sources: [ACL paper, Table 2 and Section 3.2](https://aclanthology.org/2025.acl-long.1072.pdf#page=4), [dataset construction, Appendix B](https://aclanthology.org/2025.acl-long.1072.pdf#page=13).

**Availability and rights.** The authors publish the [evaluation code](https://github.com/CoIR-team/coir), [data on Hugging Face](https://huggingface.co/CoIR-Retrieval/datasets), and a `coir-eval` Python package. The [code is Apache-2.0](https://github.com/CoIR-team/coir/blob/main/LICENSE), but the paper lists separate licenses and use conditions for its component datasets, including CC BY-SA 3.0 for StackOverflow QA and descriptions of non-commercial research use for APPS, CodeSearchNet, and CoSQA. Review the chosen subset's original rights before copying or redistributing its records; the framework license does not cover all source data. Sources: [authors' README](https://github.com/CoIR-team/coir#-data-availability), [paper, Ethical Considerations](https://aclanthology.org/2025.acl-long.1072.pdf#page=9).

**Label limits.** The authors explicitly identify the one-annotated-item-per-query design as a limitation: it cannot represent several valid answers or evidence that must be combined. The [published JavaScript qrels](https://huggingface.co/datasets/CoIR-Retrieval/CodeSearchNet-javascript-qrels) pair query and corpus IDs with relevance scores, while the [published records](https://huggingface.co/datasets/CoIR-Retrieval/CodeSearchNet-javascript-queries-corpus) contain snippet text rather than file-line evidence. CoSQA includes [zero-scored sampled pairs](https://huggingface.co/datasets/CoIR-Retrieval/cosqa-qrels); such a pair does not establish that the entire search corpus has no relevant result. The [official loader](https://github.com/CoIR-team/coir/blob/main/coir/data_loader.py) keeps only document text/title and selects `test` qrels. Consequently, adapting CoIR to JevGrep would require a separately documented mapping to licensed repository snapshots and human review of alternative and complementary evidence. Sources: [paper, Limitations](https://aclanthology.org/2025.acl-long.1072.pdf#page=9), linked data and loader.

**Held-out use.** CoIR preserves or creates train/dev/test query splits, but several subsets share origins: CodeSearchNet-CCR is derived from the same CodeSearchNet functions as the code-to-text task. The authors remove exact duplicate snippets and warn that widely used benchmarks such as CodeSearchNet can be overfit; exact deduplication does not establish freedom from near duplicates or model-training exposure. If using CoIR as an auxiliary probe, pin the dataset revision, reserve test queries until settings are frozen, avoid placing related CodeSearchNet variants on opposite sides of a split, and check source-repository overlap where provenance can be recovered. A public test score should not be described as JevGrep's independent held-out repository result. Sources: [paper, Sections 3.1–3.2 and Appendix A/B](https://aclanthology.org/2025.acl-long.1072.pdf), [official loader's test-split selection](https://github.com/CoIR-team/coir/blob/main/coir/data_loader.py).
