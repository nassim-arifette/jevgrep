# Initial local baseline — 2026-09-21

The first measured optimization candidate on this Windows workload is grouped
score-cache writes, followed by batch/payload reuse. This is a local performance
baseline with a fixed offline provider, supplemented by a separate real Vercel
retrieval pilot on 30 annotated questions.

## Setup

- Node v24.15.0, Windows x64, Intel Core i5-1135G7, eight logical CPUs.
- 64 deterministic synthetic files: 32 TypeScript, 16 Python and 16 SQL.
- Three samples, each starting a new process and isolated score cache; four ordered
  searches per sample. One provider worker, 4,000-reference-token response budget.
- Whole fixture setup, configuration loading and imports precede measurement.
  OS filesystem cache and host background activity are uncontrolled.
- Source, harness and dependency fingerprints are recorded in the raw reports.
  The runner verifies that those inputs do not change during measurement.

Reproduction:

```sh
npm run bench -- --files 64 --samples 3 --output benchmark-results/baseline-local.json
npm run bench -- --files 64 --samples 3 --no-profile --output benchmark-results/baseline-unprofiled.json
```

## Profiled results

Raw samples: [with profiling](local-windows-node24.json) and
[without profiling](local-windows-node24-unprofiled.json).

| Scenario | Median elapsed | Min–max | Simulated attempts | Reused scores | Modeled transmitted bytes |
| --- | ---: | ---: | ---: | ---: | ---: |
| First search | 20.97 s | 15.82–22.11 s | 1 | 0 | 121,858 |
| Same question | 2.57 s | 2.55–3.12 s | 0 | 64 | 0 |
| New question, unchanged files | 13.15 s | 12.67–18.38 s | 1 | 0 | 121,854 |
| Original question after one-file edit | 2.55 s | 2.04–2.87 s | 1 | 63 | 2,764 |

All searches completed and passed the expected cache-state checks. No network
requests were made. The simulated usage counts are not billed provider usage.

The separate run without profiling produced medians of 15.95 s, 2.30 s, 18.72 s
and 3.74 s respectively. Some scenarios were faster and others slower than the
profiled run; these unpaired, variable samples do not establish a reliable profiling
overhead percentage. Use the raw distributions when comparing future changes.

| Inclusive stage | First search median | New-question median |
| --- | ---: | ---: |
| Score-cache writes | 12.46 s | 8.59 s |
| Batch packing | 2.35 s | 2.04 s |
| Preparation | 2.10 s | 1.53 s |
| All tokenization, spread across stages | 2.97 s | 2.50 s |

These durations overlap and their medians can come from different samples; do not
sum them or treat them as an exclusive CPU-time breakdown. The simulated provider
does not measure real network/provider latency.

Each uncached 64-fragment search performs 64 separate cache writes and 198
engine-requested serializations containing 2,655 question entries in total.
The cold search invokes the tokenizer 7,428 times. The repeated question still
reads and chunks every file, including 32 JS/TS parses, and invokes the tokenizer
5,026 times despite reusing every score.

The timer probe cannot run until the offline search finishes in this workload.
That demonstrates sustained event-loop blocking with an immediately resolving
provider. It does not measure cancellation in a real MCP client or latency during
real provider waits.

## Next changes to measure

1. Group score-cache writes under one lock and one accounting/eviction pass per
   response. Keep cache identity, TTL, corruption recovery and concurrent-writer
   behavior covered by tests. Current `ScoreCache.write()` repeats this work for
   every score; measure the actual gain after implementing `writeMany()`.
2. Reuse serialized inputs and measured batch payloads. Preserve model-visible
   content, conservative scan caps and retry accounting.
3. Reuse preparation metadata and then persist unchanged-file preparation. Warm
   score reuse currently avoids evaluation but still repeats the local pipeline.

The ordering is specific to this initial workload. Confirm the gains after each
change, and expand to larger repositories and another operating system before
making broad performance claims. Three samples show substantial host variability.

## Live retrieval pilot

The separate [Vercel report](retrieval-vercel.json) records 30 complete searches
against `typesafe-ai/jev`, through Vercel AI Gateway, with the score cache disabled,
a relevance threshold of 0.5 and a 4,000-token response budget. It used 30 requests
and 42,479 reported input tokens, within the run caps of 60 requests and 200,000
estimated input tokens. No usage was unknown and no question was skipped.

| Metric | Result |
| --- | ---: |
| Mean evidence Recall@1, 24 positive questions | 77.8% |
| Mean evidence Recall@5 | 97.2% |
| Mean reciprocal rank | 0.979 |
| Mean evidence coverage across all returned excerpts | 97.2% |
| Complete evidence coverage per positive question | 22/24 |
| Correct empty responses, six negative questions | 6/6 |

Two cross-file queries (`subscription-04` and `subscription-07`) returned two of
their three required evidence units. Both omitted `src/cache.ts:7–9`, the actual
cache deletion implementation, while returning its caller. These are concrete
regression cases for future relevance/context-expansion work; the labels and
threshold were not tuned to these results.

These are development-pilot results on very small synthetic repositories, from a
single live run. They do not establish quality on real repositories, other languages
or full agent tasks. The requested model is a Gateway alias; the report does not
pin a resolved server-side revision. No semantic quality conclusion can be drawn
from the separate fixed-score performance runs.

## Validation

The 30-question retrieval pilot and its fixture fingerprints also validate offline.

`npm run verify` passed type checking, 419 tests (two additional tests skipped for
Windows host constraints), the build and all eight installed-artifact smoke checks.
New tests cover profiling isolation/outcome equivalence, all four cache scenarios,
annotation consistency, evidence coverage/negative metrics and aggregate provider
reservations. Detailed methodology is in [the benchmark guide](../README.md).
